# 5. 案例研究 (Case Study)

## 5.1 成功案例：级联故障定位

### 5.1.1 案例描述

**故障场景**：Online Boutique 架构中，支付服务（payment-service）因数据库连接池耗尽导致响应延迟，故障沿调用链向上游传播，影响订单服务（order-service）和 API 网关（api-gateway）。

**故障特征**：
- 3 个服务同时出现延迟升高
- 错误率从 0.1% 上升到 8%
- P99 延迟从 200ms 上升到 2500ms

**真实根因**：payment-service（数据库连接池耗尽）

### 5.1.2 CE-MARCA 推理过程

**Round 1：并行数据收集**

| 智能体 | 检测结果 | 初步假设 | 置信度 |
|--------|----------|----------|--------|
| Metrics | payment-service CPU 95%, memory 88% | payment-service | 0.75 |
| Logs | payment-service 出现"Connection pool exhausted"错误 | payment-service | 0.80 |
| Traces | payment-service 延迟 2500ms，order-service 500ms | payment-service | 0.70 |

**Round 2：因果约束推理**

协调器构建因果图：
```
api-gateway → order-service → payment-service
     │              │              │
  (15.2)        (18.7)         (root)
```

数字为 Granger 因果强度（F 统计量）。

各智能体根据因果图调整优先级，重新分析：
- Metrics 智能体：确认 payment-service 的指标异常最早出现
- Logs 智能体：发现 payment-service 的错误日志时间戳最早
- Traces 智能体：确认延迟从 payment-service 开始传播

**Round 3：假设仲裁**

协调器收集假设并仲裁：

**支付服务得分计算**：
- 基础分数：(0.75 + 0.80 + 0.70) / 3 = 0.75
- 多样性加分：0.1 × 3（3 个智能体一致）= 0.30
- 因果一致性：0.2 × 0.85（因果图中有强入边）= 0.17
- **最终得分**：0.75 + 0.30 + 0.17 = **1.22**（归一化为 0.92）

**最终报告**：
```
根因服务：payment-service
置信度：92%
因果路径：payment-service → order-service → api-gateway
推理解释：
  - metrics: CPU 95%, memory 88% (置信度：0.75)
  - logs: "Connection pool exhausted" 错误 (置信度：0.80)
  - traces: 延迟 2500ms，从 payment-service 开始传播 (置信度：0.70)
建议：
  🔴 高置信度根因：payment-service，建议立即检查数据库连接池配置
```

### 5.1.3 因果图价值分析

**对比实验**：我们对比了有无因果图的情况。

**无因果图**：
- Standard RAG 错误地将 api-gateway 识别为根因（因为它的延迟最明显）
- 原因：LLM 被表面现象误导，未识别因果传播方向

**有因果图**：
- CE-MARCA 正确识别 payment-service 为根因
- 因果图显示：payment-service → order-service → api-gateway 的传播路径
- Granger 因果检验确认：payment-service 的变化先于其他服务

**关键洞察**：
因果图通过时间先后关系和统计显著性，帮助区分"因"和"果"，避免被表面症状误导。

## 5.2 失败案例：间歇性故障

### 5.2.1 案例描述

**故障场景**：BookInfo 架构中，product-page 服务间歇性出现内存泄漏，每 10-15 分钟发生一次，持续 2-3 分钟后自动恢复。

**故障特征**：
- 内存使用率周期性波动（60% → 90% → 60%）
- 无明显错误日志
- 延迟轻微上升（200ms → 400ms）

**真实根因**：product-page（内存泄漏）

### 5.2.2 CE-MARCA 推理过程

**Round 1**：
- Metrics 智能体：检测到内存波动，但置信度低（0.55）
- Logs 智能体：未检测到明显错误（置信度 0.30）
- Traces 智能体：延迟变化不显著（置信度 0.45）

**Round 2**：
协调器扩大时间窗口（30min → 1h），重新分析：
- Metrics 智能体：发现周期性模式，置信度提升到 0.65
- Logs 智能体：仍无明显错误
- Traces 智能体：延迟变化仍不显著

**Round 3**：
仲裁结果：
- product-page 得分：0.58（低于阈值 0.75）
- 最终输出：无法确定根因（unknown）

### 5.2.3 失败原因分析

**1. 故障模式识别不足**：
- 间歇性故障的特征不明显，故障分类器未能准确识别
- 周期性模式需要更长时间窗口（>2h）才能检测

**2. 日志证据缺失**：
- 内存泄漏未产生明显错误日志
- Logs 智能体无法提供有效证据

**3. 因果图质量受限**：
- 间歇性故障导致时间序列不平稳
- Granger 因果检验假设平稳性，效果下降

### 5.2.4 改进方向

**1. 增强故障模式识别**：
- 引入频域分析（傅里叶变换）检测周期性
- 使用变化点检测算法识别间歇性故障

**2. 改进日志分析**：
- 使用更敏感的异常检测（如孤立森林）
- 结合日志语义分析，识别潜在警告

**3. 非平稳因果发现**：
- 使用适用于非平稳时间序列的因果发现方法
- 考虑分段因果分析

## 5.3 用户研究（初步）

我们邀请 3 名运维工程师评估 CE-MARCA 的可解释性。

**评估任务**：
- 阅读 10 个故障的 RCA 报告
- 评分：可解释性（1-5 分）、可信度（1-5 分）、实用性（1-5 分）

**结果**：

| 工程师 | 可解释性 | 可信度 | 实用性 | 反馈 |
|--------|----------|--------|--------|------|
| 工程师 A（5 年经验） | 4.5 | 4.0 | 4.5 | "因果路径清晰，帮助理解故障传播" |
| 工程师 B（3 年经验） | 4.0 | 4.5 | 4.0 | "置信度评分让我知道何时需要人工介入" |
| 工程师 C（8 年经验） | 4.0 | 3.5 | 4.5 | "建议措施实用，但希望看到更多上下文" |

**平均评分**：可解释性 4.2 / 可信度 4.0 / 实用性 4.3

**定性反馈**：
- **优点**：因果路径可视化、多智能体证据汇总、置信度评分
- **改进建议**：增加历史故障对比、提供更详细的时间线

## 5.4 本章小结

通过案例研究，我们深入分析了 CE-MARCA 的推理过程：
1. **成功案例**：因果图帮助区分因果传播方向，避免被表面症状误导
2. **失败案例**：间歇性故障检测仍是挑战，需要改进故障模式识别
3. **用户反馈**：可解释性和实用性获得认可，可信度需进一步提升
